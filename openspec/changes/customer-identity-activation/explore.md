# Exploration: customer-identity-activation (customer login/identity redesign — guest → activated account)

## Locked context (do not re-litigate — see orchestrator's design conversation)

Goal: let a guest booker self-activate a real account (OTP/magic-link primary, Google/Apple OAuth primary, password secondary) scoped per `organizationId`, with `customers.authUserId` added as a real FK for solidity. Two real orgs (Lourdes, Gloria) stay fully isolated; the "one org, many professionals" framing is a future-platform rule, not a change to today's two tenants. TICKET CUST-01 (`/me/citas` professional attribution) is explicitly out of scope. Full rationale for these decisions already lives in HEARTBEAT.md's `2026-09-18 #10` entry and is not reproduced here.

## 1. Full map of current customer-identity touchpoints

- **`apps/web/src/app/(auth)/login/actions.ts` (`loginAction`)** — confirmed: `signInWithPassword` only. Resolves `x-tenant-slug` → org → checks `profiles` (staff, exact org match) → `/dashboard`; else `customers` by lower-cased email in that org → `/me`; else signs the user out and returns `no_account`. `resolveRedirectUrl()` validates `next` against the org's own subdomain (open-redirect guard) — this pattern must be preserved by any new activation redirect logic.
- **`apps/web/src/app/(auth)/login/_components/LoginForm.tsx`** — password-only, `href="#"` dead "forgot password" link (confirmed line 137), no signup/activation entry point. `showBookCta` only appears on `no_account`, pointing to `/book`.
- **`apps/web/src/app/(tenant)/[tenant]/book/actions.ts` (`createBooking`, guest upsert ~lines 264-294)** — selects existing `customers` row by `(organizationId, email)`; inserts `{ organizationId, fullName, email, phone, isGuest: true }` if none exists. **No Supabase Auth call anywhere in this file.** No `authUserId` write (column doesn't exist yet). This path is genuinely guest-only, confirming the orchestrator's premise for the *pure-guest* case.
- **`apps/web/src/domains/customers/service-me.ts`** — `getMyCustomer(organizationId, email)`, `getMyAppointments(organizationId, customerId)` (joins `catalogServices` for name/price/currency, per TICKET CUST-01 no `staffProfileId` join), `updateMyProfile(...)` (sets `isGuest: false` — this is the *only* existing "promote guest to registered" signal in the codebase, and it's a side effect of a profile edit, not an explicit activation flow). All three query via `db` (Drizzle direct Postgres connection) — **not** through Supabase's RLS-governed REST/JS client (see §4, this matters).
- **`apps/web/src/proxy.ts`** — `/me` auth+tenant guard already landed (TICKET MW-03, `openspec/changes/mw-03-me-auth-guard-proxy/`, archived). `AUTH_REQUIRED_PREFIXES = ['/dashboard', '/admin', '/me']` returns a real 307 to `buildLoginUrl()` when unauthenticated; `PRIVATE_PREFIXES` (locale-chain only) deliberately excludes `/me`. Any new activation route under `/me/*` or `/login/*` needs to be placed relative to these two prefix lists deliberately (`/login/*` subroutes stay outside `AUTH_REQUIRED_PREFIXES`, `/me/*` stays behind it).
- **`apps/web/src/app/(tenant)/[tenant]/_components/UserMenu.tsx`** — unauthenticated state links plainly to `/login` (line 61, `href="/login"`, no query params). Authenticated state already renders an OAuth avatar (`user.avatarUrl`) when present — see §2, this is not theoretical, it is live.
- **`apps/web/src/shared/lib/resolve-public-session.ts` (`resolvePublicSessionUser`)** — feeds `UserMenu`. Already merges `user.user_metadata.avatar_url`/`picture`/`full_name`/`name` (OAuth claims) with the `profiles`/`customers` row, falling back staff-then-customer, tenant-scoped. This is the piece of code the orchestrator's brief undercounted: **OAuth identity data is already flowing into the UI**, just not yet into `customers.authUserId`.
- **`apps/web/src/app/auth/callback/route.ts`** — a working PKCE OAuth callback (`exchangeCodeForSession`), redirecting to `?next=` (default `/book`) or `/book?auth_error=1` on failure. Generic — not `/book`-specific by construction, reusable for a `/login`-initiated OAuth flow with a different `next`.

### Correction to the orchestrator's brief: a second, pre-existing customer auth surface

**`apps/web/src/app/(tenant)/[tenant]/book/_components/Step2Auth.tsx` is a second, already-shipped customer-auth entry point that the brief's "zero Auth linkage exists" framing did not account for.** During booking (Step 2), the guest is offered: Google OAuth (`supabase.auth.signInWithOAuth({ provider: 'google' })`, live), an email/password login (`signInWithPassword`), an email/password **registration** (`supabase.auth.signUp({ email, password, options: { data: { full_name } } })`), or "continue as guest." Apple is scaffolded in HEARTBEAT (Phase 27, "Auth-aware step skipping in `/book` funnel", DONE 2026-04-22) but the button is commented out in the JSX with `{/* Apple — pendiente de Apple Developer membership */}` — confirmed dead in the file, so Apple truly is zero-code-blocked (external console only), matching the brief's framing for Apple specifically, not for Google.

**Security-relevant gap this surfaces, directly touching locked decision #5**: `handleRegister` in `Step2Auth.tsx` is exactly the "type your email, set a password" pattern decision #5 calls an account-takeover vector — it calls bare `supabase.auth.signUp` with no OTP/magic-link verification step first. Whether this is exploitable depends on the project's Supabase Auth "Confirm email" setting (unconfirmed users normally can't sign in until they click the emailed confirmation link) — I could not verify that dashboard toggle from code or SQL. **This existing `/book` registration path is a live instance of the exact pattern the new `/login` activation flow is designed to avoid, and should be either migrated to the new OTP-first flow or explicitly reconciled with it — flagging as a proposal-phase decision, not deciding it here.** It is also not linked to the guest `customers` row created earlier in the same booking flow by anything other than a later post-hoc email match — there is no code in `book/actions.ts` or `Step3Confirm.tsx`/`Step2Auth.tsx` that writes `user.id` onto the `customers` row today (consistent with `authUserId` not existing yet).

Also unresolved by current code: whether a Google-OAuth-authenticated guest's `customers` row (created via the later booking upsert, matched by `user.email`) gets any different treatment than a bare guest — reading `book/actions.ts`'s upsert (§ above), it does not; it is an identical email-matched upsert regardless of how `input.guestEmail`'s owner authenticated. This confirms there is genuinely no `authUserId` linkage anywhere yet, matching the brief's core premise even though the *auth surface itself* (Google OAuth, password signup) already exists.

## 3. Supabase identity-linking across OTP / OAuth / password for the same email — flagged as unverified, recommend `sdd-research`

I could not verify with high confidence, from code or the Supabase docs available to me in this exploration pass, exactly how Supabase Auth resolves the same email address when a person first verifies via OTP, later signs in via Google OAuth, and later sets a password — specifically: does `auth.users` end up as **one** row (auto-linked) or does Supabase create a second `auth.users` row for the OAuth identity unless "manual linking" (`supabase.auth.linkIdentity`) is explicitly used? This is a well-documented Supabase Auth nuance (identity linking policy differs by project setting and has changed across Supabase Auth versions), and getting it wrong would silently break the "one person, one `authUserId`" assumption the whole activation design leans on. **This is exactly the kind of externally-documented, version-sensitive behavior `sdd-research` exists for — flagging it as the recommended next step for this specific question, not deciding or guessing an answer here.**

One related fact I *did* verify empirically: this project's own `auth.users` already contains 5 distinct rows for 5 distinct emails, each with a single `provider` in `raw_app_meta_data` (`email` ×4, `google` ×1) — no case of one email spanning two providers exists yet in this dataset, so the live data can't answer the linking question either; it would need to be tested directly (create a test user via OTP, then attempt Google sign-in with the same email, inspect `auth.identities`) or confirmed against current Supabase documentation.

## 4. RLS check — verified against the live database, not assumed from repo SQL

The repo's checked-in SQL (`apps/web/supabase/drizzle-migrations/`, `apps/web/supabase/migrations/`) contains no `CREATE POLICY` statements at all — RLS policies are not managed as code in this repo. Queried live instead (`pg_policies`):

```
customers:    customers_org_all    (ALL) USING (organization_id IN (SELECT profiles.organization_id FROM profiles WHERE profiles.id = auth.uid()))
appointments: appointments_org_all (ALL) USING (organization_id IN (SELECT profiles.organization_id FROM profiles WHERE profiles.id = auth.uid()))
```

**Important finding, not simply a confirmation**: both policies grant access only through a `profiles` row match — i.e., **only staff** (`profiles.id = auth.uid()`) get any RLS-granted access to `customers`/`appointments`. A customer's own `auth.uid()` never appears in `profiles`, so **RLS today grants a signed-in customer zero rows on either table.** This means the "org-scoped isolation" the customer-facing app currently relies on (`getMyCustomer`, `getMyAppointments`, the `/book` guest upsert) is enforced **entirely by application-layer `organizationId` filters in hand-written Drizzle queries running over a direct/service Postgres connection that bypasses RLS**, not by the database. This is consistent with — and reinforces the necessity of — locked decision #4 (cross-tenant activation isolation must be enforced at the application layer, not assumed from Supabase): it already has to be, today, for staff-vs-customer separation too, since RLS doesn't cover the customer path at all currently.

Practical implication for the design phase: adding `customers.authUserId` does not, by itself, get any RLS protection for free. If any future client-side/customer-authenticated Supabase call is ever added against `customers`/`appointments` directly (none exists today — `service-me.ts` and `book/actions.ts` are both server-only, `db`-based), a customer-scoped RLS policy keyed off `customers.authUserId = auth.uid()` (once that column exists) would need to be written from scratch; today there is nothing to extend. Not a blocker for this change (server-only access continues to work exactly as it does now), but worth the design phase explicitly deciding whether to add a customer-self RLS policy proactively (defense-in-depth) or leave RLS staff-only and keep trusting server-only access paths, matching current practice.

Schema-level note relevant to `authUserId`'s design: `customers` has **no unique constraint** on `(organizationId, email)` today (confirmed via `pg_constraint` on the live table — only a PK, an org FK, and a `client_status` check constraint exist). The guest-upsert flow in `book/actions.ts` relies on a `SELECT` immediately followed by an `INSERT` with no unique constraint backing it, so a race between two concurrent guest bookings with the same email could already create two `customers` rows for one person today. This preexists this change and is not proposed to be fixed here, but the design phase should decide up front which existing row (if duplicates exist for a given email) an activation flow's `authUserId` link targets, and whether adding the FK column is a good moment to also add the missing unique constraint (recommended, but a design decision, not made here).

## 5. Activation trigger options (surveyed, not decided)

Two independent entry points, not mutually exclusive:

- **Self-serve, customer-initiated**: a banner/CTA inside `/me` (once a guest is already viewing their booking confirmation, e.g. `book/success`, or inside `/me/perfil`) offering "activate your account" — natural fit since `updateMyProfile()` already flips `isGuest: false` as a side effect of editing the profile, suggesting the codebase already has an implicit "this guest just became more permanent" moment to hook into. Also naturally fits `/login` itself once OTP/OAuth become primary: a guest with no password today would simply "log in" via OTP/OAuth and the login flow itself performs the activation (match by email → link `authUserId`), no separate "activate" screen needed. This is likely the primary path given decision #1's framing ("login into `/me`").
- **Staff-triggered invite**: an "Invite to activate account" action from the dashboard's customer detail view (`(dashboard)/dashboard/customers/[id]/...`), sending an OTP/magic-link email to a guest customer's address on the staff member's behalf. Useful for high-touch scenarios (a staff member wants a regular walk-in client to have online self-service) but adds dashboard UI + a new server action, and touches RBAC (who can trigger it — likely Owner/Staff both, per IDENTITY.md §5, no restriction obviously needed, but worth confirming explicitly in the proposal).
- Both can coexist without conflict since they converge on the same underlying mechanism (send OTP/magic-link, on verification link `authUserId` to the matching `customers` row in that org). Deciding which to build first (or both) is a proposal-phase product-scoping decision, not made here.
